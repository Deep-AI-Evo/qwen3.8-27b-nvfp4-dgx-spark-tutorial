## 3. 性能测试（`vllm bench serve`，random 数据集）

### 3.1 单流（实测）

- 解码速度 **≈ 11.9 tokens/s**（思考模式长输出）
- 短提示 TTFT **0.18s**

### 3.2 并发压测（输入 512 / 输出 128，32 条请求）

| 指标 | 并发 8 | 并发 16 |
|---|---|---|
| 成功率 | 32/32 | 32/32 |
| 输出吞吐 | **72.0 tok/s**（峰值 88） | **115.7 tok/s**（峰值 160） |
| 总吞吐（含 prefill） | 359.9 tok/s | 578.7 tok/s |
| 平均 TTFT | 1.66 s | 2.46 s |
| 平均 TPOT | 98.6 ms | 119.1 ms |
| 耗时 | 56.9 s | 35.4 s |

### 3.3 长上下文（输入 8192 / 输出 256，4 条，并发 2）

- 平均 TTFT 4.84 s（8k prefill），P99 7.0 s
- prefill + decode 合计吞吐 555 tok/s（折算 prefill 约 1900 tok/s）
- TPOT 99.9 ms，与短上下文基本一致

### 3.4 资源占用

- 统一内存占用约 110GB / 119GB（vLLM 按 0.85 预分配，含权重 23.4GB + KV cache）
- 空闲功耗 13W，温度 48℃

## 3.5 MTP 推测解码优化（已启用）

模型自带 MTP 头（`model_mtp.safetensors`，1 层全注意力），启动参数加
`--speculative-config '{"method":"mtp","num_speculative_tokens":3}'` 后实测：

| 场景 | 无 MTP | MTP ×3 | 提升 |
|---|---|---|---|
| 单流·思考模式数学推理 | 11.8 tok/s | **22.7 tok/s** | **+92%** |
| 单流·非思考长文写作 | ≈12 tok/s | **16.7 tok/s** | ≈+40% |
| 并发 8 聚合输出吞吐 | 72.0 tok/s | 77.7 tok/s | +8%（无回退） |
| 并发 8 TPOT | 98.6 ms | 78.8 ms | -20% |

- 草稿接受率：真实文本 54%–84%（逐位置 0.86/0.69/0.55），平均接受长度 2.1–3.1 tokens/步；
  随机 token 压测数据接受率仍有 39.5%，且并发场景吞吐无回退。
- `num_speculative_tokens` 对比：×2 与 ×3 单流速度基本打平（21.4 vs 22.7 tok/s），
  ×2 在难预测文本上开销更小，×3 在可预测文本（代码、格式化输出）上峰值更高；最终采用 ×3。

### 3.6 并发 1–4 日常场景实测（256k 配置 + MTP ×3，输入 512 / 输出 256）

| 指标 | 并发 1 | 并发 2 | 并发 4 |
|---|---|---|---|
| 单流解码速度（1/TPOT） | **21.6 tok/s** | **16.0 tok/s** | **15.0 tok/s** |
| 聚合输出吞吐 | 20.0 tok/s | 22.7 tok/s | 44.0 tok/s |
| 平均 TTFT（512 输入） | 0.99 s | 0.81 s | 1.92 s（中位 0.75 s） |
| TPOT（均值/中位） | 46.3 / 46.3 ms | 62.7 / 61.2 ms | 66.6 / 54.6 ms |

注：压测用随机 token 文本，MTP 接受率（37%–59%）低于真实文本，真实对话的单流速度会更接近
3.5 节实测的 17–23 tok/s。短提示 TTFT ≈0.6–1.0s，主要为固定开销（含 MTP 草稿前向）。

### 3.7 上下文长度衰减实测（单并发，256k 配置 + MTP ×3）

| 上下文（输入） | TTFT | prefill 速度 | TPOT | 单流解码 |
|---|---|---|---|---|
| 1k | 0.57 s | **≈1800 tok/s** | 83.0 ms | ≈12–21 tok/s* |
| 8k（此前 64k 配置实测） | 4.2 s | ≈1900 tok/s | 99.9 ms（无 MTP） | — |
| 100k | 83.0 s | **≈1230 tok/s**（-32%） | 60.1 ms（+30%） | **≈16.6 tok/s** |
| 200k | 244.1 s | **≈840 tok/s**（-53%） | 70.3 ms（+52%） | **≈14.2 tok/s** |
| **256k（261,000 tokens，实测顶格）** | 365.9 s | **≈715 tok/s**（-60%） | 87.5 ms（+88%） | **≈11.4 tok/s** |

\* 1k 组随机数据 MTP 接受率偏低（18%），TPOT 失真；真实文本参考 3.5/3.6 节。

结论：

- **解码衰减很平缓**：256K 顶格上下文下解码仍有 1k 时的约 6–7 成速度。这得益于混合架构——
  64 层中 48 层是 Gated DeltaNet 线性注意力（解码成本与上下文长度无关），仅 16 层全注意力随长度增长。
- **prefill 随长度明显变慢**：2 倍上下文耗时约 3 倍（全注意力层二次方项显现）。
  100k 灌入约 1.4 分钟、200k 约 4 分钟、256k 顶格约 6 分钟，属于"可接受但要避免频繁重复灌入"的水平。
- **256K 上下文真实性已验证**：大海捞针测试（255,376 tokens，针在 70% 深度）一次命中，
  证明该配置下模型确实能利用完整上下文，而非仅"能跑不崩"。
- 该混合架构 vLLM 当前不支持前缀缓存（`enable_prefix_caching=False`），
  同一文档的重复问答**每轮只需增量 prefill 新增对话部分**，KV cache 内已有内容不会重算；
  但新会话重新灌入同一长文档需重新 prefill。

## 4. 部署中发现的问题与解决

| 问题 | 原因 | 解决 |
|---|---|---|
| huggingface.co 直连不通 | 网络限制 | 改用 hf-mirror.com 镜像下载 |
| `Python.h: No such file or directory` | 系统缺 `python3.12-dev` 且无 root | `apt-get download` + `dpkg -x` 本地解包，启动时设 `CPATH` |
| `FileNotFoundError: 'ninja'` | 启动 PATH 未含 venv/bin | 启动命令显式加 `PATH=.../qwen38-env/bin:$PATH` |
| 思考链混入 content 并残留 `</think>` | 未启用 reasoning parser | 加 `--reasoning-parser qwen3`（本版响应字段名为 `reasoning`） |
| `vllm bench` 卡住无请求 | `--tokenizer` 用模型 ID 触发 HF 联网 | 改为本地分词器路径 |

## 5. 结论

1. **部署可行**：Qwen3.8-27B-NVFP4 可在 DGX Spark（GB10）上以纯 pip 方式部署，无需 root、无需 Docker，全程约 30 分钟（含 23GB 下载）。
2. **功能完整**：文本（思考/非思考/流式/多轮）、视觉理解、代码生成均正常，回答质量符合 27B 级别预期。
3. **性能定位（256k 上下文 + MTP）**：单流解码 15–23 tok/s，200k 长上下文下仍有约 14 tok/s；短文本 prefill 约 1800–1900 tok/s，100k 灌入约 1.4 分钟、200k 约 4 分钟；并发 8 聚合输出约 78–116 tok/s。
4. **最终配置已启用完整 262,144 tokens 上下文**，KV cache 209 万 tokens，满长上下文下支持约 8 路并发。

## 6. 日常使用建议（基于以上实测）

1. **并发数**：
   - 个人交互 1–2 路（单流 16–23 tok/s，高于阅读速度）；
   - 挂多个 Agent/会话控制在 **4 路以内**（单流仍 ≥15 tok/s）；
   - 8 路是交互体验上限；批量离线任务可用 16 路以上吃满聚合吞吐。
2. **长上下文（核心目标 256k）**：
   - 服务已按 262,144 tokens 配置，直接可用，无需调参。
   - **100k 以内随意用**（灌入约 1.4 分钟）；**200k 级留给"一次灌入、多轮问答"的场景**
     （如整库代码、长文档分析），首问等约 4 分钟，后续每轮只需增量 prefill，解码约 14 tok/s。
   - 避免在多个新会话里反复灌同一长文档（无前缀缓存，每次全量重算）。
   - 满 256k 上下文最多同时 8 路；日常长短混合使用时 KV cache 按实际占用分配，无需手动管理。
3. **模式选择**：复杂推理/代码用思考模式（质量高，22.7 tok/s）；闲聊/翻译/摘要关思考
   （`chat_template_kwargs.enable_thinking=false`，更快更省 token）。
4. **采样参数**：用官方推荐值（思考 1.0/0.95/20；非思考 0.7/0.8/20 + presence_penalty 1.5），
   长输出务必给足 `max_tokens`。
